# Wktbox Branding and v0.3.0 Release Design

**Date:** 2026-07-24

## Goal

Add the complete user-provided Wktbox logo package to the repository, display
the appropriate logo in the main README, remove the source ZIP, and publish
the resulting source and runtime artifacts as Wktbox v0.3.0.

## Branding assets

The package contents belong under `docs/assets/branding/`. This keeps
documentation and identity files separate from `assets/`, which is a Go
package containing the embedded sandbox Compose template.

All eleven image files are retained:

- square icons in SVG and 128, 512, and 1024 pixel PNG variants;
- a monochrome square SVG;
- compact horizontal PNG and SVG variants;
- light-background horizontal PNG and SVG variants;
- dark-background horizontal PNG and SVG variants.

The package guide becomes `docs/assets/branding/README.md`. The source archive
`WKTBox-logo-package (1).zip` is deleted after extraction and must not appear
in the committed tree.

## README presentation

The top of `README.md` uses a centered HTML `picture` element before the
existing heading and badges:

- dark browser themes select `wktbox-logo-dark.svg`;
- light browser themes and the fallback select `wktbox-logo-light.svg`;
- alternative text is `Wktbox — isolated dev environments`;
- the rendered width is 720 pixels while remaining responsive to the README
  viewport.

The Markdown heading remains present for accessibility, document structure,
search, and plain-text renderers.

## Release contents and version

The next version is `v0.3.0`. It is a SemVer minor release because it adds
backwards-compatible features after `v0.2.0`:

- bidirectional and transactional port forwarding;
- an always-running graphical Chromium with a per-box CDP endpoint;
- the Wktbox branding package and README identity.

`CHANGELOG.md` moves these entries from `Unreleased` into a dated `0.3.0`
section and updates comparison links. Release notes are generated from this
section by `.github/workflows/release.yml`.

## Verification and publication

Before publication:

- verify every expected branding file exists and the README references both
  theme-aware SVGs;
- verify the source ZIP is absent;
- run formatting, unit tests, vet, documentation checks, image tests, E2E,
  and `make release-dry-run VERSION=0.3.0`;
- confirm no unrelated untracked file is committed.

Publication order:

1. push the reviewed `main` commit to `origin/main`;
2. wait for the main CI workflow to succeed;
3. create annotated tag `v0.3.0` on that exact commit and push only the tag;
4. wait for the tag-triggered release workflow to complete;
5. verify the public GitHub Release, its nine expected assets, checksums,
   installable binary version, and both public multi-architecture runtime
   images.

If CI fails, the tag is not created. If the release workflow fails after the
tag is published, inspect the failing job and avoid moving or recreating the
tag when immutable artifacts may already exist.
